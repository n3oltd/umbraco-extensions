**✅ (2026-07-24) — Perplex v4 "Invalid content key" for nested media editors FIXED via a value-editor replacement; strongly-typed block rendering verified.**

Umbraco's own block editor sets both keys; Perplex doesn't. **Reported upstream 2026-07-24 → issue [#102](https://github.com/PerplexDigital/Perplex.ContentBlocks/issues/102) + fix [PR #103](https://github.com/PerplexDigital/Perplex.ContentBlocks/pull/103)** (maintainer @PerplexDaniel confirmed the cause and aims to release the fix early the following week). Not fixed in 4.0.1/4.0.2 (those only touch frontend TS; `ContentBlocksValueEditor.cs` unchanged) — **remove the workaround once the upstream fix ships in a release we can upgrade to.**

**⚠️ DECISION NEEDED (2026-07-23) — Perplex.ContentBlocks v4 is LTS-only → evaluate migrating blocks to native Umbraco Block List.** *(Note only — held; no code changed, no migration started.)*
- **Vendor constraint:** `Perplex.ContentBlocks` v4 supports **Umbraco 17 (LTS) / .NET 10 only**, and Perplex's own repo/docs state there are **no plans to support non-LTS versions (Umbraco 18–20)**. Staying on Perplex therefore **pins block content to the LTS-only release cadence** — if N3O ever moves to a non-LTS Umbraco, Perplex will not follow. The suggested mitigation is to migrate off Perplex to first-party **Umbraco Block List / Block Grid**, which is supported on every version.
- **What v4 already changed (in the migrated code):** NestedContent → Block Editor under the hood; `IContentBlockDefinition.DataTypeKey`/`DataTypeId` removed, `ElementTypeKey` added. Our `v17-Talha` code is already on the v4 API (`ElementTypeKey => Id`, `BlockNameTemplate`), and the old per-block NestedContent data-type creation (`PerplexBlockTypesService.CreateDataTypes`) was correctly dropped — v4 has no per-block data type (see the `TODO Migration Review` at `Blocks.Perplex/Services/PerplexBlockTypesService.cs:35`, which is resolvable, not a gap).
- **Existing-content reality (read-only SQL on the live v13 DBs, 2026-07-23):** AFH (`eu1-actionforhumanity-uk-v2-staging`) = 2 `Perplex.ContentBlocks` editors + 129 `Umbraco.NestedContent` wrapper data types + **607 populated block properties**; Mercy Relief (`eu1-mercyrelief-uk-staging`) = 1 editor + 87 NC wrappers + **293 populated** (largest single value ~78 KB). v3 stores each block's content as an embedded **NestedContent item** (`ncContentTypeAlias` + sibling prop values, inner editor values in v13 formats). **Perplex ships no content-migration tool/guide** (confirmed: release notes, GitHub issues, docs). Element-type keys are **stable** across versions (deterministic `UmbracoId.Generate`, `Key = definition.Id` in both v13 and v17), so a converter needs no remap table. This content migration is a **run-once data migration** best folded into the existing NestedContent→Block List CLI (`N3ONestedContentMigrationPlan`), **not** the Blocks per-project PR.
- **Decision to make:** **(A)** stay on Perplex.ContentBlocks v4 (accept LTS-only lock-in, ship as-is), or **(B)** migrate the Perplex blocks to native Umbraco Block List/Grid (removes the third-party LTS dependency, but requires building + running the content data migration above across all client sites). Either way the Blocks *code* migration (per-project PR) is unaffected — this is a separate strategic/content decision.
